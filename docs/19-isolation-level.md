# 19 · 隔离级别与四种并发问题

> **一句话价值**：把脏读、不可重复读、幻读、丢失更新逐个亲手复现，并知道自己的业务该选哪个隔离级别。

**难度**：⭐⭐⭐⭐　|　**时长**：约 40 分钟　|　**涉及表**：`users`、`orders`

## 什么时候你会遇到它

你查「用户余额 100」，与此同时另一个人转走了钱，于是你「读到」了一个**从未存在过**的余额 —— 你按这个数做了决策。或者反过来：同一个事务里查两次库存，一次有货一次没货，代码自己把自己绕晕了。

这些事故全是「两个窗口同时动手」引起的，和 SQL 写得对不对没关系。这篇把四种问题逐个复现给你看。

## 1. 先开两个窗口（新手最容易懵的一步）

后面每条 SQL 都标了「窗口 1」或「窗口 2」，**照着标号执行**。开法：两个终端窗口各执行一遍 ——

```powershell
docker exec -it easy-mysql mysql -uroot -peasy123 -t --default-character-set=utf8mb4 easy_mysql
```

（图形界面的话，Adminer 开两个浏览器标签页效果一样。）

三条规矩，先记住：

1. **事务是连接级别的**：窗口 1 `START TRANSACTION` 之后改的数据，窗口 2 默认看不见 —— 这既是隔离性的原理，也是你必须开两个窗口的原因
2. **一个窗口同一时刻只有一个事务**：窗口 1 没 `COMMIT` / `ROLLBACK` 之前，它后面的 SQL 都憋在同一个事务里
3. **每个实验做完，两个窗口都执行 `ROLLBACK;`**，再做下一个

下面所有实验都拿 `orders` 表的 1 号订单开刀，它原始金额是 2663.13：

```sql
-- 窗口 1
SELECT id, amount FROM orders WHERE id = 1;
```

```text
+----+---------+
| id | amount  |
+----+---------+
|  1 | 2663.13 |
+----+---------+
```

## 2. 问题一：脏读（Dirty Read）—— 读到别人还没提交的数据

**先证明默认级别下你根本复现不出来。** MySQL 默认 `REPEATABLE READ`，两边什么都不用设置：

```sql
-- 窗口 1
START TRANSACTION;
UPDATE orders SET amount = 99999 WHERE id = 1;   -- 不提交，停住
SELECT NOW(6) AS 持有起始时刻 FROM DUAL;
SELECT SLEEP(8);
ROLLBACK;
SELECT NOW(6) AS 已回滚时刻 FROM DUAL;
```

```sql
-- 窗口 2（在窗口 1 停住期间执行）
START TRANSACTION;
SELECT NOW(6) AS 读取时刻 FROM DUAL;
SELECT amount AS 窗口2读到 FROM orders WHERE id = 1;
ROLLBACK;
```

```text
+----------------------------+
| 持有起始时刻               |
+----------------------------+
| 2026-10-08 13:17:05.903776 |
+----------------------------+
+----------+
| SLEEP(8) |
+----------+
|        0 |
+----------+
+----------------------------+
| 已回滚时刻                 |
+----------------------------+
| 2026-10-08 13:17:13.926275 |
+----------------------------+
```

```text
+----------------------------+
| 读取时刻                   |
+----------------------------+
| 2026-10-08 13:17:08.988066 |
+----------------------------+
+---------------+
| 窗口2读到     |
+---------------+
|       2663.13 |
+---------------+
```

时间戳对得上：窗口 2 在 `13:17:08` 读，正落在窗口 1 持有未提交数据的 `05.90 → 13.92` 之间 —— **但它读到的是旧值 2663.13**。默认级别把脏读挡死了。

`READ COMMITTED` 级别同样挡得住（窗口 2 先切到 RC，再重复刚才的读）：

```sql
-- 窗口 2（窗口 1 照旧持有未提交的 99999）
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT NOW(6) AS 读取时刻 FROM DUAL;
SELECT amount AS RC读到 FROM orders WHERE id = 1;
```

```text
+----------------------------+
| 读取时刻                   |
+----------------------------+
| 2026-10-08 13:19:09.696037 |
+----------------------------+
+----------+
| RC读到   |
+----------+
|  2663.13 |
+----------+
```

**想看到脏读，必须先降级。** 两个窗口都执行：

```sql
-- 窗口 1 和 窗口 2 都执行
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

然后重复刚才那两段 SQL：

```text
+----------------------------+
| 读取时刻                   |
+----------------------------+
| 2026-10-08 13:17:31.969566 |
+----------------------------+
+---------------+
| 窗口2读到     |
+---------------+
|      99999.00 |
+---------------+
```

这次窗口 2 读到了 **99999.00** —— 窗口 1 还没提交、马上要 `ROLLBACK` 的值。**这就是脏读（Dirty Read）：读到了别人还没提交的数据。**

等窗口 1 回滚完，再查一次：

```sql
-- 窗口 2
SELECT amount AS 回滚后再读 FROM orders WHERE id = 1;
```

```text
+-----------------+
| 回滚后再读      |
+-----------------+
|         2663.13 |
+-----------------+
```

你拿着 99999 做的决策，对应的那笔钱**从来就没有存在过**。

> **脏读为什么能发生**：`READ UNCOMMITTED` 级别下，读的一方不看别人的事务，直接读数据的最新状态 —— 相当于「别人写到一半的草稿你也直接看」。

## 3. 问题二：不可重复读（Non-repeatable Read）—— 同一事务里读两次结果不一样

两个窗口都切成 `READ COMMITTED`：

```sql
-- 窗口 1 和 窗口 2 都执行
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

```sql
-- 窗口 1
START TRANSACTION;
SELECT NOW(6) AS 第一次读的时刻, amount AS 第一次读 FROM orders WHERE id = 1;
SELECT SLEEP(8);
SELECT NOW(6) AS 第二次读的时刻, amount AS 第二次读 FROM orders WHERE id = 1;
ROLLBACK;
```

```sql
-- 窗口 2（在窗口 1 的 SLEEP 期间执行，autocommit 会自动提交）
UPDATE orders SET amount = 88888 WHERE id = 1;
SELECT NOW(6) AS 窗口2提交时刻, amount AS 窗口2提交后 FROM orders WHERE id = 1;
```

```text
+----------------------------+------------------+
| 窗口2提交时刻              | 窗口2提交后      |
+----------------------------+------------------+
| 2026-10-08 12:58:55.575325 |         88888.00 |
+----------------------------+------------------+
```

```text
+----------------------------+--------------+
| 第一次读的时刻             | 第一次读     |
+----------------------------+--------------+
| 2026-10-08 12:58:52.479621 |      2663.13 |
+----------------------------+--------------+
+----------+
| SLEEP(8) |
+----------+
|        0 |
+----------+
+----------------------------+--------------+
| 第二次读的时刻             | 第二次读     |
+----------------------------+--------------+
| 2026-10-08 12:59:00.481460 |     88888.00 |
+----------------------------+--------------+
```

（窗口 2 的提交时刻 `12:58:55.57` 夹在两次读 `52.47` 和 `00.48` 中间。）

**同一个事务、同一条 SQL，读出来 2663.13 和 88888.00 两个数 —— 这就是不可重复读（Non-repeatable Read）：事务期间别人提交了修改，你的两次读不一致。**

对照组：两个窗口都换回默认的 `REPEATABLE READ` 再做一遍 ——

```text
+----------------------------+--------------+
| 第一次读的时刻             | 第一次读     |
+----------------------------+--------------+
| 2026-10-08 12:59:14.299793 |      2663.13 |
+----------------------------+--------------+
+----------------------------+--------------+
| 第二次读的时刻             | 第二次读     |
+----------------------------+--------------+
| 2026-10-08 12:59:22.301508 |      2663.13 |
+----------------------------+--------------+
```

第二次读**还是 2663.13**，哪怕窗口 2 在 `12:59:17` 已经把 88888 提交了。这就是「可重复读」这四个字的字面意思。

## 4. 问题三：幻读（Phantom Read）—— 同样的查询，行数凭空变了

先把基线归零（这个范围里本来一张单都没有）：

```sql
-- 窗口 1
SELECT COUNT(*) AS 8到9万之间的订单 FROM orders WHERE amount BETWEEN 80000 AND 90000;
```

```text
+-------------------------+
| 8到9万之间的订单        |
+-------------------------+
|                       0 |
+-------------------------+
```

```sql
-- 窗口 1（READ COMMITTED）
START TRANSACTION;
SELECT NOW(6) AS 第一次查的时刻, COUNT(*) AS 第一次计数 FROM orders WHERE amount BETWEEN 80000 AND 90000;
SELECT SLEEP(8);
SELECT NOW(6) AS 第二次查的时刻, COUNT(*) AS 第二次计数 FROM orders WHERE amount BETWEEN 80000 AND 90000;
ROLLBACK;
```

```sql
-- 窗口 2（在 SLEEP 期间执行）
INSERT INTO orders (user_id, product_id, quantity, amount, status, created_at, updated_at)
VALUES (1, 1, 1, 85000, 'paid', NOW(), NOW());
SELECT NOW(6) AS 窗口2插入时刻, id AS 新订单id FROM orders WHERE amount = 85000;
```

```text
+----------------------------+-------------+
| 窗口2插入时刻              | 新订单id    |
+----------------------------+-------------+
| 2026-10-08 12:59:41.411148 |      202001 |
+----------------------------+-------------+
```

```text
+----------------------------+-----------------+
| 第一次查的时刻             | 第一次计数      |
+----------------------------+-----------------+
| 2026-10-08 12:59:38.311368 |               0 |
+----------------------------+-----------------+
+----------+
| SLEEP(8) |
+----------+
|        0 |
+----------+
+----------------------------+-----------------+
| 第二次查的时刻             | 第二次计数      |
+----------------------------+-----------------+
| 2026-10-08 12:59:46.352591 |               1 |
+----------------------------+-----------------+
```

**同一条 SQL、同一个事务，0 变成了 1 —— 多出来的这行就是「幻影」，问题叫幻读（Phantom Read）：事务期间别人插了新行，你的两次范围查询对不上。**

对照组：默认 `REPEATABLE READ` 下重复同样操作，窗口 2 的插入变成 —

```text
+----------------------------+-------------+
| 窗口2插入时刻              | 新订单id    |
+----------------------------+-------------+
| 2026-10-08 13:00:05.129865 |      202002 |
+----------------------------+-------------+
```

窗口 1 的两次计数：

```text
+----------------------------+-----------------+
| 第一次查的时刻             | 第一次计数      |
+----------------------------+-----------------+
| 2026-10-08 13:00:02.010618 |               0 |
+----------------------------+-----------------+
+----------------------------+-----------------+
| 第二次查的时刻             | 第二次计数      |
+----------------------------+-----------------+
| 2026-10-08 13:00:10.053301 |               0 |
+----------------------------+-----------------+
```

第二次还是 0（窗口 2 在 `13:00:05` 明明插进去了）。实验完的窗口 2 把幻影行删掉了：`SELECT COUNT(*) FROM orders;` = **200000**，回到基线。

## 5. 问题四：丢失更新（Lost Update）—— 谁都不是脏读，结果还是丢了

前三个问题隔离级别能管，第四个**管不了**，所以单拎出来。两个窗口都按「先查出来、在程序里算、再写回去」的老套路：

```sql
-- 窗口 1
START TRANSACTION;
SELECT NOW(6) AS 读取时刻, balance AS 窗口1读到 FROM users WHERE id = 1;
SELECT SLEEP(8);
UPDATE users SET balance = 6401.78 WHERE id = 1;   -- 程序算的：6201.78 + 200
COMMIT;
```

```sql
-- 窗口 2（在窗口 1 的 SLEEP 期间执行）
START TRANSACTION;
SELECT balance AS 窗口2读到 FROM users WHERE id = 1;
UPDATE users SET balance = 6301.78 WHERE id = 1;   -- 程序算的：6201.78 + 100
COMMIT;
SELECT NOW(6) AS 窗口2写回时刻 FROM DUAL;
```

```text
+---------------+
| 窗口2读到     |
+---------------+
|       6201.78 |
+---------------+
+----------------------------+
| 窗口2写回时刻              |
+----------------------------+
| 2026-10-08 13:18:19.787835 |
+----------------------------+
```

```text
+----------------------------+------------------+
| 写回时刻                   | 窗口1写回后      |
+----------------------------+------------------+
| 2026-10-08 13:18:24.680610 |          6401.78 |
+----------------------------+------------------+
```

两个窗口都读到 6201.78。窗口 2 在 `13:18:19` 先提交 6301.78，窗口 1 在 `13:18:24` 后提交 6401.78。两边都结束后查最终值：

```sql
SELECT balance AS 最终余额 FROM users WHERE id = 1;
```

```text
+--------------+
| 最终余额     |
+--------------+
|      6401.78 |
+--------------+
```

**6401.78 —— 窗口 2 那笔 +100 被整个盖掉，凭空消失。** 两边都没读错、没写错、没有脏读，更新还是丢了：这就是丢失更新（Lost Update）。

它不是隔离级别的管辖范围，解法是写操作前加 `SELECT ... FOR UPDATE` 把行锁住 —— 第 20 篇整篇都在讲锁。

（实验后我已把余额还原成 6201.78，`SUM(balance)` 校验过。）

## 6. 四种隔离级别对照表 + 怎么切换

上面所有现象，数据库用**隔离级别（Isolation Level）**一档一档地控制：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| READ UNCOMMITTED | 会 | 会 | 会 |
| READ COMMITTED | 不会 | 会 | 会 |
| REPEATABLE READ | 不会 | 不会 | 基本不会（间隙锁） |
| SERIALIZABLE | 不会 | 不会 | 不会（但并发性能极差） |

这张表的前两行，第 2、3、4 节已经全部实测过。第四行也测：

```sql
-- 窗口 1
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
START TRANSACTION;
SELECT NOW(6) AS 开始读的时刻, COUNT(*) AS 计数 FROM users WHERE age > 0;
SELECT SLEEP(8);
ROLLBACK;
```

```sql
-- 窗口 2（在窗口 1 持有事务期间执行）
SELECT NOW(6) AS 更新前时刻 FROM DUAL;
UPDATE users SET age = age WHERE id = 1;
SELECT NOW(6) AS 更新后时刻 FROM DUAL;
```

```text
+----------------------------+
| 更新前时刻                 |
+----------------------------+
| 2026-10-08 13:00:35.596138 |
+----------------------------+
+----------------------------+
| 更新后时刻                 |
+----------------------------+
| 2026-10-08 13:00:40.520629 |
+----------------------------+
```

窗口 1 只是一句普通 `SELECT`，窗口 2 的 `UPDATE` 就被堵了将近 5 秒（直到窗口 1 在 `40.50` 回滚才放行）。**SERIALIZABLE 把读也变成锁，最干净，也最堵** —— 这就是表格里「并发性能极差」的实测版本。

**切换命令**（`SET SESSION` 只影响当前窗口，退出即失效）：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT @@transaction_isolation AS 切换后;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT @@transaction_isolation AS 改回默认;
```

```text
+----------------+
| 切换后         |
+----------------+
| READ-COMMITTED |
+----------------+
+-----------------+
| 改回默认        |
+-----------------+
| REPEATABLE-READ |
+-----------------+
```

**MySQL 的默认值**：

```sql
SELECT @@transaction_isolation AS 本会话级别, @@global.transaction_isolation AS 全局默认;
```

```text
+-----------------+-----------------+
| 本会话级别      | 全局默认        |
+-----------------+-----------------+
| REPEATABLE-READ | REPEATABLE-READ |
+-----------------+-----------------+
```

会话和全局都是 `REPEATABLE-READ` —— 这是 MySQL 和 Oracle / PostgreSQL（默认 RC）最大的不同点，很多人从别的数据库迁过来第一件事就是被它「坑」。

## 7. RR 怎么把幻读压住的：间隙锁一句话版

RR 之下你看到的普通 `SELECT` 走的是 **MVCC（多版本并发控制）**：读的人看的是自己事务开始时的快照，别人提交的新行根本不在快照里 —— 所以不可重复读、幻读都「看不见」。

但快照只管普通读。`UPDATE`、`SELECT ... FOR UPDATE` 这类**当前读**必须读最新数据，这时 RR 靠**间隙锁（Gap Lock）**：把范围里「存在的行」和「行与行之间的空隙」一起锁住，别人连插都插不进来。第 20 篇有实测：锁住 `id BETWEEN 3 AND 6` 之后，另一个窗口 `INSERT id = 5` 会卡 5 秒。

## 8. 选级建议：绝大多数业务用默认的 RR 就够

- **默认 `REPEATABLE READ`，别改**。快照读 + 间隙锁，脏读、不可重复读出不来，幻读也被压住大半。课程设计、教务系统、商城下单，这一档全够
- **什么时候才用 `READ COMMITTED`**：你需要「永远读到最新提交的数据」，比如计数器页、刚提交立刻回显的场景。它放弃了可重复读，换来更少的锁冲突
- **`SERIALIZABLE`**：除非你正在写数据库教材，否则别碰 —— 实测一句读就能堵死别人的写
- **`READ UNCOMMITTED`**：只在排查问题时临时用一下，业务上等价于「不设防」

## 三个必须记住的结论

1. **四种并发问题的共同根源是「两个事务同时读写同一批数据」**：脏读读到未提交、不可重复读读到已提交的改动、幻读多出新行、丢失更新被后写者覆盖
2. **MySQL 默认 RR 下，脏读 / 不可重复读 / 幻读 三个都复现不出来** —— 本篇每一条「读到的值」都是双会话实跑的，时间戳能对上
3. **隔离级别只管前三个问题**；丢失更新要靠 `SELECT ... FOR UPDATE` 加锁解决，那是第 20 篇的事

## 常见错误

### ❌ 级别名拼错一个字母

```sql
-- ERROR 1064 (42000): You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'UNCOMMITED' at line 1
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITED;
```

**为什么错**：`UNCOMMITED` 少了个 `T`，MySQL 的解析器把它当成不认识的关键字，直接语法报错 —— 你的窗口还停在原来的级别上，后面的实验现象会全部对不上。

**正确做法**（四个名字一个字母都不能差，注意都是空格不是下划线）：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```
