# 17 · 联合索引与最左前缀：三个字段只建一个索引

> **一句话价值**：搞懂 `(a,b,c)` 这个索引到底能用在哪些查询上，并顺手解决「优化器选错索引」。

**难度**：⭐⭐⭐⭐　|　**时长**：约 35 分钟　|　**涉及表**：`orders`、`orders_slow`

## 什么时候你会遇到它

你建了 `(status, created_at, user_id)` 三列索引，查 `WHERE user_id = 42`，`EXPLAIN` 却显示 `type=index`，把 20 多万行的索引从头扫一遍；把三个条件全写上，扫出来的行数又由 `created_at` 的范围说了算，`user_id` 只能在结果里挨个挑。索引里明明有这一列，它却像不存在 —— 这背后是一条硬规则：**最左前缀**。

## 本篇你会学到

- [ ] 联合索引的**排序规则**（先按 a 排，a 相同再按 b 排）
- [ ] 范围查询会「截断」后面的列
- [ ] 排序方向（`ASC` / `DESC`）对联合索引的影响
- [ ] 索引下推（Index Condition Pushdown）一句话版
- [ ] **优化器选错索引怎么办**：`FORCE INDEX` 与改写 SQL

## 1. 本质：把三列当成一个「组合键」排序

`(c1, c2, c3)` 不是三个索引拼一起，是**一棵按三列组合值排序的 B+ 树**。实验先用 6 行小表把顺序看清楚：

```sql
CREATE INDEX b_idx ON idx_demo (c1, c2, c3);
SELECT c1, c2, c3 FROM idx_demo ORDER BY c1, c2, c3;
```

```text
+------+------+------+
| c1   | c2   | c3   |
+------+------+------+
| a    | x    | m    |
| a    | y    | a    |
| a    | y    | z    |
| b    | x    | a    |
| b    | x    | c    |
| b    | y    | q    |
+------+------+------+
```

先按 `c1` 分组，组内按 `c2` 排，再按 `c3` 排。推论很重要：索引里「天然有序」的只有**整条组合键的顺序**，所以哪些查询能用上它、哪一列能免排序，全由列的先后位置决定。下面拿 20 万行的表实测。

## 2. 最左前缀：6 条查询，6 个 EXPLAIN

实验在 `orders_slow`（`orders` 的双胞胎，唯一区别是没有二级索引）上建三列索引 —— 优化器手里只有它一个二级索引，不会被抢走：

```sql
ALTER TABLE orders_slow ADD INDEX idx_status_created_user (status, created_at, user_id);
```

```sql
-- ① 三列全用上
SELECT id FROM orders_slow WHERE status = 'paid' AND created_at >= '2024-01-01' AND user_id = 42;
-- ② 用上第 1、2 列
SELECT id FROM orders_slow WHERE status = 'paid' AND created_at >= '2024-01-01';
-- ③ 只用第 1 列
SELECT id FROM orders_slow WHERE status = 'paid';
-- ④ 跳过第 1 列，直查第 3 列
SELECT id FROM orders_slow WHERE user_id = 42;
-- ⑤ 跳过第 1 列，直查第 2 列
SELECT id FROM orders_slow WHERE created_at >= '2024-01-01';
-- ⑥ status 用 IN（本质仍是等值）+ created_at 范围
SELECT id FROM orders_slow
WHERE status IN ('paid', 'shipped') AND created_at >= '2024-11-01';
```

① 三列全用上 —— `key_len=14`：

```text

+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
```

② 用上第 1、2 列 —— `key_len=6`：

```text
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
| id | select_type | table       | partitions | type  | possible_keys           | key                     | key_len | ref  | rows  | filtered | Extra                    |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | range | idx_status_created_user | idx_status_created_user | 6       | NULL | 96582 |   100.00 | Using where; Using index |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
```

③ 只用第 1 列 —— `key_len=1`：

```text
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+--------------------------+
| id | select_type | table       | partitions | type | possible_keys           | key                     | key_len | ref   | rows  | filtered | Extra                    |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | ref  | idx_status_created_user | idx_status_created_user | 1       | const | 96582 |   100.00 | Using where; Using index |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+--------------------------+
```

`key_len` 每多用一列就涨一段：`status` 是 `ENUM` 占 1 字节、`created_at` 是 `DATETIME` 占 5 字节、`user_id` 是 `BIGINT` 占 8 字节 —— 14 = 1 + 5 + 8（①），6 = 1 + 5（②⑤⑥），1 = 只有 `status`（③）。

④ 跳过第 1 列直查第 3 列 —— 没法定位，整个索引从头扫：

```text
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+--------+----------+--------------------------+
| id | select_type | table       | partitions | type  | possible_keys           | key                     | key_len | ref  | rows   | filtered | Extra                    |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+--------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | index | idx_status_created_user | idx_status_created_user | 14      | NULL | 203574 |    10.00 | Using where; Using index |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+--------+----------+--------------------------+
```

⑤ 跳过第 1 列直查第 2 列 —— MySQL 8 拿 skip scan 兜底：

```text
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+----------------------------------------+
| id | select_type | table       | partitions | type  | possible_keys           | key                     | key_len | ref  | rows  | filtered | Extra                                  |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+----------------------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | range | idx_status_created_user | idx_status_created_user | 6       | NULL | 67851 |   100.00 | Using where; Using index for skip scan |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+----------------------------------------+
```

⑥ `status` 用 `IN` —— 本质还是等值，和 ② 一样用到前两列：

```text
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
| id | select_type | table       | partitions | type  | possible_keys           | key                     | key_len | ref  | rows  | filtered | Extra                    |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | range | idx_status_created_user | idx_status_created_user | 6       | NULL | 30436 |   100.00 | Using where; Using index |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
```

六条放一起看：

| 查询 | 用上第几列 | key_len | rows | 说明 |
|---|---|---|---|---|
| ① 三列条件全写 | 3 列全用 | 14 | 96582 | `range` 起点用到三列 |
| ② `status` + `created_at` 范围 | 2 列 | 6 | 96582 | 正常的最左前缀 |
| ③ 只有 `status` | 1 列 | 1 | 96582 | `ref` + `const`，最好的一种 |
| ④ 只有 `user_id` | 0 列（定位不了） | 14（当扫描宽度） | 203574 | `type=index`，整索引从头扫 |
| ⑤ 只有 `created_at` 范围 | skip scan 兜底 | 6 | 67851 | 跳过 `status` 的几个取值逐段试 |
| ⑥ `status IN (...)` + `created_at` 范围 | 2 列 | 6 | 30436 | `IN` 本质仍是等值 |

**规则：跳过前缀列就失去了「定位」能力；`IN` 算等值；能用到几列，`key_len` 一量就知道。**

## 3. 范围截断：范围之后的列只能过滤

```sql
-- ① 第 3 列 user_id 是等值
SELECT id FROM orders_slow
WHERE status = 'paid' AND created_at >= '2024-11-01' AND user_id = 42;
-- ② 第 3 列换成范围
SELECT id FROM orders_slow
WHERE status = 'paid' AND created_at >= '2024-11-01' AND user_id BETWEEN 40 AND 60;
```

```text
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
| id | select_type | table       | partitions | type  | possible_keys           | key                     | key_len | ref  | rows  | filtered | Extra                    |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | range | idx_status_created_user | idx_status_created_user | 14      | NULL | 15256 |    10.00 | Using where; Using index |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
```

```text
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
| id | select_type | table       | partitions | type  | possible_keys           | key                     | key_len | ref  | rows  | filtered | Extra                    |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | range | idx_status_created_user | idx_status_created_user | 14      | NULL | 15256 |    11.11 | Using where; Using index |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+-------+----------+--------------------------+
```

两条唯一的差别是 `filtered`：10.00 → 11.11。`user_id` 怎么变，`key_len` 和 `rows` 都纹丝不动 —— **`created_at` 是范围，它之后的列就进不了「定位」环节**，估算行数仍由 `created_at` 的范围决定，`user_id` 只写在 `filtered` 里当事后过滤器。真跑一遍看实际扫描量：

```text
*************************** 1. row ***************************
EXPLAIN: -> Filter: ((orders_slow.`status` = 'paid') and (orders_slow.created_at >= TIMESTAMP'2024-11-01 00:00:00') and (orders_slow.user_id between 40 and 60))  (cost=3093 rows=1695) (actual time=0.306..3.77 rows=38 loops=1)
    -> Covering index range scan on orders_slow using idx_status_created_user over (status = 'paid' AND '2024-11-01 00:00:00' <= created_at AND 40 <= user_id)  (cost=3093 rows=15256) (actual time=0.263..2.67 rows=8229 loops=1)
```

实扫 8229 行（`created_at` 范围里的所有行），在其中挑出 `user_id` 命中的 38 行。同样的条件换到 `orders` 表，优化器的选择完全不同：

```text
+----+-------------+--------+------------+-------+-------------------------------------------+-----------------+---------+------+------+----------+------------------------------------+
| id | select_type | table  | partitions | type  | possible_keys                             | key             | key_len | ref  | rows | filtered | Extra                              |
+----+-------------+--------+------------+-------+-------------------------------------------+-----------------+---------+------+------+----------+------------------------------------+
|  1 | SIMPLE      | orders | NULL       | range | idx_orders_user,idx_orders_status_created | idx_orders_user | 8       | NULL |  649 |     7.51 | Using index condition; Using where |
+----+-------------+--------+------------+-------+-------------------------------------------+-----------------+---------+------+------+----------+------------------------------------+
```

```text
*************************** 1. row ***************************
EXPLAIN: -> Filter: ((orders.`status` = 'paid') and (orders.created_at >= TIMESTAMP'2024-11-01 00:00:00'))  (cost=292 rows=48.8) (actual time=0.261..1.23 rows=38 loops=1)
    -> Index range scan on orders using idx_orders_user over (40 <= user_id <= 60), with index condition: (orders.user_id between 40 and 60)  (cost=292 rows=649) (actual time=0.255..1.16 rows=649 loops=1)
```

它选了 `idx_orders_user`，范围从 `user_id` 起步，实扫 649 行 —— 比 8229 小一个数量级还多。这次优化器选对了。设计规则跟着出来了：**等值列放前面，范围列放后面**；范围列之后的列，既不能定位，也拿不到索引的顺序（下一节马上验证）。

## 4. 排序也能用索引（还有索引下推）

先看 `orders_slow` 没有二级索引时的样子 —— `ORDER BY` 只能自己排：

```text
+----+-------------+-------------+------------+------+---------------+------+---------+------+--------+----------+-----------------------------+
| id | select_type | table       | partitions | type | possible_keys | key  | key_len | ref  | rows   | filtered | Extra                       |
+----+-------------+-------------+------------+------+---------------+------+---------+------+--------+----------+-----------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 203574 |    25.00 | Using where; Using filesort |
+----+-------------+-------------+------------+------+---------------+------+---------+------+--------+----------+-----------------------------+
```

**① 排序列在索引里**（`WHERE status='paid' ORDER BY created_at`）—— `Using filesort` 消失：

```text
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+--------------------------+
| id | select_type | table       | partitions | type | possible_keys           | key                     | key_len | ref   | rows  | filtered | Extra                    |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | ref  | idx_status_created_user | idx_status_created_user | 1       | const | 96582 |   100.00 | Using where; Using index |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+--------------------------+
```

**② 换个排序列 `amount`**（不在索引里）—— `Using filesort` 回来了：

```text
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+---------------------------------------+
| id | select_type | table       | partitions | type | possible_keys           | key                     | key_len | ref   | rows  | filtered | Extra                                 |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+---------------------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | ref  | idx_status_created_user | idx_status_created_user | 1       | const | 96582 |   100.00 | Using index condition; Using filesort |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+---------------------------------------+
```

**③ 范围之后的列，排序也吃不到**（`created_at` 范围 + `ORDER BY user_id`）—— `key_len=6`，`filesort` 甩不掉：

```text
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+------+----------+------------------------------------------+
| id | select_type | table       | partitions | type  | possible_keys           | key                     | key_len | ref  | rows | filtered | Extra                                    |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+------+----------+------------------------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | range | idx_status_created_user | idx_status_created_user | 6       | NULL | 4106 |   100.00 | Using where; Using index; Using filesort |
+----+-------------+-------------+------------+-------+-------------------------+-------------------------+---------+------+------+----------+------------------------------------------+
```

**④ 反方向排也不用 filesort**（`ORDER BY created_at DESC`）：

```text
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+-----------------------------------------------+
| id | select_type | table       | partitions | type | possible_keys           | key                     | key_len | ref   | rows  | filtered | Extra                                         |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+-----------------------------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | ref  | idx_status_created_user | idx_status_created_user | 1       | const | 96582 |   100.00 | Using where; Backward index scan; Using index |
+----+-------------+-------------+------------+------+-------------------------+-------------------------+---------+-------+-------+----------+-----------------------------------------------+
```

`Backward index scan` = MySQL 8 反着扫一遍索引。结论：**排序方向和索引顺序一致（全正向或全反向）都不用 filesort，混着来才要额外排**。

最后一块拼图 —— 索引下推（Index Condition Pushdown，ICP）：

```text
+----+-------------+--------+------------+-------+---------------------------+---------------------------+---------+------+------+----------+-----------------------+
| id | select_type | table  | partitions | type  | possible_keys             | key                       | key_len | ref  | rows | filtered | Extra                 |
+----+-------------+--------+------------+-------+---------------------------+---------------------------+---------+------+------+----------+-----------------------+
|  1 | SIMPLE      | orders | NULL       | range | idx_orders_status_created | idx_orders_status_created | 6       | NULL | 2181 |   100.00 | Using index condition |
+----+-------------+--------+------------+-------+---------------------------+---------------------------+---------+------+------+----------+-----------------------+
```

`Using index condition` 就是 ICP：`status`、`created_at` 这些条件先在索引页里筛完，剩下的行才回表 —— 见到它说明过滤已经推到存储层，回表次数变少，是好事。

## 5. 优化器选错索引：真实案例

```sql
SELECT id, user_id FROM orders
WHERE status = 'paid' AND user_id BETWEEN 1 AND 100 ORDER BY user_id;
```

优化器默认选了 `idx_orders_status_created`：

```text
+----+-------------+--------+------------+------+-------------------------------------------+---------------------------+---------+-------+-------+----------+----------------------------------------------------+
| id | select_type | table  | partitions | type | possible_keys                             | key                       | key_len | ref   | rows  | filtered | Extra                                              |
+----+-------------+--------+------------+------+-------------------------------------------+---------------------------+---------+-------+-------+----------+----------------------------------------------------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_orders_user,idx_orders_status_created | idx_orders_status_created | 1       | const | 95652 |    49.08 | Using index condition; Using where; Using filesort |
+----+-------------+--------+------------+------+-------------------------------------------+---------------------------+---------+-------+-------+----------+----------------------------------------------------+
```

强制换成 `idx_orders_user` 再看 —— 注意 `rows` 变成了 **1**，强制之后估算已经失真，只能 `EXPLAIN ANALYZE` 真跑：

```text
+----+-------------+--------+------------+-------+-----------------+-----------------+---------+------+------+----------+------------------------------------+
| id | select_type | table  | partitions | type  | possible_keys   | key             | key_len | ref  | rows | filtered | Extra                              |
+----+-------------+--------+------------+-------+-----------------+-----------------+---------+------+------+----------+------------------------------------+
|  1 | SIMPLE      | orders | NULL       | range | idx_orders_user | idx_orders_user | 8       | NULL |    1 |    33.33 | Using index condition; Using where |
+----+-------------+--------+------------+-------+-----------------+-----------------+---------+------+------+----------+------------------------------------+
```

```text
+--------------------------------------------------+
| 实验                                           |
+--------------------------------------------------+
| --- §6-① 真跑一遍（EXPLAIN ANALYZE）--- |
+--------------------------------------------------+
*************************** 1. row ***************************
EXPLAIN: -> Sort: orders.user_id  (cost=5295 rows=95652) (actual time=73.6..74.1 rows=10823 loops=1)
    -> Filter: (orders.user_id between 1 and 100)  (cost=5295 rows=95652) (actual time=7.34..71.4 rows=10823 loops=1)
        -> Index lookup on orders using idx_orders_status_created (status='paid'), with index condition: (orders.`status` = 'paid')  (cost=5295 rows=95652) (actual time=7.34..68.6 rows=50000 loops=1)

+--------------------------------------------------+
| 实验                                           |
+--------------------------------------------------+
| --- §6-② 真跑一遍（EXPLAIN ANALYZE）--- |
+--------------------------------------------------+
*************************** 1. row ***************************
EXPLAIN: -> Filter: (orders.`status` = 'paid')  (cost=0.71 rows=0.333) (actual time=0.0446..50.8 rows=10823 loops=1)
    -> Index range scan on orders using idx_orders_user over (1 <= user_id <= 100), with index condition: (orders.user_id between 1 and 100)  (cost=0.71 rows=1) (actual time=0.0221..47.8 rows=43168 loops=1)
```

默认计划实扫 50000 行再 filesort，74.1 毫秒；强制后实扫 43168 行、没有 filesort，50.8 毫秒 —— 这一次优化器确实选错了。但先别急着抄 `FORCE INDEX`：第 16 篇同一查询的另一轮实测只快了 15 毫秒（74.1 → 59.5），收益随缓存和数据分布浮动，而估算在强制后已经失真。**`FORCE INDEX` 是止痛药，根治靠把索引建对**（第 7 节的设计题）。

## 6. 别滥用 FORCE INDEX：用错了比不用还惨

```sql
SELECT id FROM orders
WHERE status = 'paid' AND created_at >= '2024-12-15' AND user_id BETWEEN 1 AND 100;
```

默认计划 —— `created_at` 范围先筛掉绝大部分行：

```text
+----+-------------+--------+------------+-------+-------------------------------------------+---------------------------+---------+------+------+----------+------------------------------------+
| id | select_type | table  | partitions | type  | possible_keys                             | key                       | key_len | ref  | rows | filtered | Extra                              |
+----+-------------+--------+------------+-------+-------------------------------------------+---------------------------+---------+------+------+----------+------------------------------------+
|  1 | SIMPLE      | orders | NULL       | range | idx_orders_user,idx_orders_status_created | idx_orders_status_created | 6       | NULL | 2181 |    49.08 | Using index condition; Using where |
+----+-------------+--------+------------+-------+-------------------------------------------+---------------------------+---------+------+------+----------+------------------------------------+
```

强制 `user_id` 索引 —— `rows=1` 又是失真的估算：

```text
+----+-------------+--------+------------+-------+-----------------+-----------------+---------+------+------+----------+------------------------------------+

+----+-------------+--------+------------+-------+-----------------+-----------------+---------+------+------+----------+------------------------------------+
|  1 | SIMPLE      | orders | NULL       | range | idx_orders_user | idx_orders_user | 8       | NULL |    1 |    11.11 | Using index condition; Using where |

```

```text
    -> Index range scan on orders using idx_orders_user over (1 <= user_id <= 100), with index condition: (orders.user_id between 1 and 100)  (cost=0.71 rows=1) (actual time=0.0147..47.9 rows=43168 loops=1)
```

默认实扫 2181 行、2.9 毫秒；强制后实扫 43168 行、51.4 毫秒 —— **慢了 17 倍多**。同一批强制，第 5 节赚了、这里赔惨，因为这次它替你否掉的恰好是优化器的正确判断。动用 `FORCE INDEX` 的顺序：先看索引列序能不能改对 → 再看 SQL 怎么改写 → 实在要临时强制，记下来过段时间复查。

## 7. 动手练参考答案：给三类查询设计索引

```sql
-- A. WHERE status=?                         → (status)
-- B. WHERE status=? ORDER BY created_at     → (status, created_at) —— 基线索引 idx_orders_status_created 正是它
-- C. WHERE user_id=? ORDER BY created_at    → (user_id, created_at)
```

给 C 建上 `(user_id, created_at)` 实测：

```text
+----+-------------+--------+------------+------+----------------------------------+------------------+---------+-------+------+----------+-------------+
| id | select_type | table  | partitions | type | possible_keys                    | key              | key_len | ref   | rows | filtered | Extra       |
+----+-------------+--------+------------+------+----------------------------------+------------------+---------+-------+------+----------+-------------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_orders_user,idx_user_created | idx_user_created | 8       | const |   29 |   100.00 | Using index |
+----+-------------+--------+------------+------+----------------------------------+------------------+---------+-------+------+----------+-------------+
```

对照 —— 强制原来的单列索引，`ORDER BY` 立刻回到 filesort：

```text
+----+-------------+--------+------------+------+-----------------+-----------------+---------+-------+------+----------+----------------+
| id | select_type | table  | partitions | type | possible_keys   | key             | key_len | ref   | rows | filtered | Extra          |
+----+-------------+--------+------------+------+-----------------+-----------------+---------+-------+------+----------+----------------+
|  1 | SIMPLE      | orders | NULL       | ref  | idx_orders_user | idx_orders_user | 8       | const |   29 |   100.00 | Using filesort |
+----+-------------+--------+------------+------+-----------------+-----------------+---------+-------+------+----------+----------------+
```

29 行上两者的快慢看不出来，差别在规模：走组合索引读满 10 条就停，filesort 至少要把 `WHERE` 命中的行全读一遍才排得出前 10。至于「按状态查时间范围」和「按用户查时间范围」要同时快 —— 一个索引只有一个第一列，没法同时当两个前缀，答案是**两个联合索引**：`(status, created_at)`（基线已有）+ `(user_id, created_at)`（本节新建，实验跑完即删）。

## 三个必须记住的结论

1. **最左前缀是排序规则，不是玄学**：`(a,b,c)` 是一把组合尺，等值条件从左往右用；跳过前缀列就失去定位能力，`key_len` 一量就知道用到第几列
2. **范围在哪列断，后面的列就只能陪跑**：不能再定位、也拿不到索引顺序（`ORDER BY` 照样 filesort）—— 等值列在前，范围列在后
3. **`FORCE INDEX` 是止痛药不是修复**：`rows=1` 的失真、17 倍的反噬都是实测 —— 先改索引列序，再改写 SQL，最后才强制

## 常见错误

### ❌ 删索引时名字不存在

```sql
DROP INDEX idx_not_exist ON orders;
-- ERROR 1176 (42000): Key 'idx_not_exist' doesn't exist in table 'orders'
```

**为什么错**：`DROP INDEX` 按名字删，名字打错、或者这个索引已经被前面的实验清掉了，都会撞 1176。

**正确做法**：动手前 `SHOW INDEX FROM orders_slow;` 确认名字。配套实验的临时索引用完即删，重复执行没问题；自己手动管理索引时，先查再删。

## 动手练

- [ ] 设计一个能同时支持「按状态查时间范围」和「按用户查时间范围」的联合索引（答案在第 7 节）
- [ ] 用 `key_len` 验证列序：把 `idx_status_created_user` 换成 `(created_at, status, user_id)`，重跑第 2 节的 6 条查询，对比 `key_len` 和 `rows`（做完把索引改回来）
- [ ] 想一想：⑤ 只查 `created_at` 能用 skip scan 兜底，④ 只查 `user_id` 为什么只能全索引扫？（提示：skip scan 要逐个跳过前缀列的取值，`status` 一共几个取值？`created_at` 呢？）

<details>
<summary>第 1 题的答案</summary>

**两个联合索引，一个不够**：`(status, created_at)`（基线里的 `idx_orders_status_created` 就是它）+ `(user_id, created_at)`。

一个索引只有一根最左起点，`(status, created_at, user_id)` 也救不了「按用户查时间范围」—— `user_id` 排在第三位，两种查询都得跳列（第 2 节的 ④ 就是现场：`type=index`，整索引从头扫）。第 7 节有实测：建 `(user_id, created_at)` 后 `EXPLAIN` 是 `key_len=8`、`Using index`，而强制原来的单列索引立刻回到 `Using filesort`。

</details>

<details>
<summary>第 2 题的答案</summary>

换列序的现场（在第 2 节的基础上先删旧索引再建，跑完删干净）：

```sql
-- 第 2 节的 idx_status_created_user 还在就先删掉（不在会报 1176，见「常见错误」）
ALTER TABLE orders_slow DROP INDEX idx_status_created_user;
ALTER TABLE orders_slow ADD INDEX idx_swap (created_at, status, user_id);
-- 重跑第 2 节的 6 条 EXPLAIN 后：
ALTER TABLE orders_slow DROP INDEX idx_swap;   -- 收尾 orders_slow 必须只剩 PRIMARY
```

6 条查询换序前后的真实对照（前 3 列格式：`type` / `key_len` / `rows`）：

| 查询 | `(status, created_at, user_id)` | `(created_at, status, user_id)` |
|---|---|---|
| ① 三列条件全写 | range / 14 / 96582 | range / 14 / 101787 |
| ② `status` + `created_at` 范围 | range / 6 / 96582 | range / 6 / 101787 |
| ③ 只有 `status` | **ref / 1 / 96582** | **index / 14 / 203574**（全索引扫） |
| ④ 只有 `user_id` | index / 14 / 203574 | index / 14 / 203574 |
| ⑤ 只有 `created_at` 范围 | skip scan / 6 / 67851 | **range / 5 / 101787**（直接定位） |
| ⑥ `status IN` + 时间范围 | range / 6 / 30436 | range / 6 / 68148 |

最惨的是 ③：`status` 从第一列挪到第二列，从最好的 `ref`（`key_len=1`、`ref=const`）跌成全索引扫：

```text
+----+-------------+-------------+------------+-------+---------------+----------+---------+------+--------+----------+--------------------------+
| id | select_type | table       | partitions | type  | possible_keys | key      | key_len | ref  | rows   | filtered | Extra                    |
+----+-------------+-------------+------------+-------+---------------+----------+---------+------+--------+----------+--------------------------+
|  1 | SIMPLE      | orders_slow | NULL       | index | idx_swap      | idx_swap | 14      | NULL | 203574 |    25.00 | Using where; Using index |
+----+-------------+-------------+------------+-------+---------------+----------+---------+------+--------+----------+--------------------------+
```

最赚的是 ⑤：`created_at` 升为前导列，`key_len=5` 直接 `range` 定位，不再靠 skip scan 兜底。

**列序没有绝对好坏，谁排第一谁被定位。** 所以排顺序的依据是查询频率：最高频的等值列放最前，范围列放它后面 —— 这就是第 3 节那条「等值在前、范围在后」的由来。

</details>

<details>
<summary>第 3 题的答案</summary>

先量前缀列的取值数：

```sql
SELECT COUNT(DISTINCT status), COUNT(DISTINCT created_at), COUNT(*) FROM orders_slow;
```

```text
+-----------------+---------------------+--------+
| status_distinct | created_at_distinct | total  |
+-----------------+---------------------+--------+
|               4 |              200000 | 200000 |
+-----------------+---------------------+--------+
```

skip scan 的本质是「把前缀列的不同取值当跳跃点，逐段试」：

- ⑤ 要跳的前缀只有 `status` —— **4 个取值，跳 4 段就完事**，所以 `Extra` 里有 `Using index for skip scan`
- ④ 要跳 `status` × `created_at` —— 4 × 200000 = **80 万段，比整张表的行数还多**，跳比扫还贵，优化器直接放弃定位，`type=index` 从头扫整个索引

第 2 题里换序后的 ③ 也是同一个病：`status` 前面隔着 20 万个 `created_at` 取值，一个也跳不动。**skip scan 只在前缀列取值很少时才兜得住** —— 这也正是把低区分度的 `status` 放索引第一位不吃亏的原因。

</details>
