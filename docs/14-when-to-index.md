# 14 · 哪些该建索引，哪些不该：一张决策表

> **一句话价值**：拿到一个字段，能立刻判断该不该给它建索引、建成什么类型。

**难度**：⭐⭐⭐　|　**时长**：约 30 分钟　|　**涉及表**：`orders`、`users`、`scores`

## 什么时候你会遇到它

你给表的每个字段都加了索引，结果表膨胀到 2 倍，`INSERT` 慢了一截，`EXPLAIN` 显示 `key = NULL` 索引根本没用上。

## 本篇你会学到

- [ ] 该建索引的三类字段：主键、外键、WHERE/ORDER BY 里反复出现的字段
- [ ] **不该建**的情况（低区分度字段、写多读少的表）
- [ ] 联合索引的顺序为什么重要（最左前缀）
- [ ] 索引失效的 8 种写法（背下来能省很多时间）
- [ ] 索引不是越多越好：真实的取舍演示

## 正文大纲

1. **`status` 这种字段要不要建索引**（本篇主菜）
   ```sql
   -- 4 个值 = 25% 的行，优化器会认为它不如全表扫描
   SELECT status, COUNT(*) FROM orders GROUP BY status;
   ```
2. **区分度怎么量**：
   ```sql
   SELECT COUNT(DISTINCT user_id) / COUNT(*) FROM orders;   -- 越接近 1 越好
   ```
3. **联合索引与最左前缀**：
   ```sql
   KEY idx (a, b, c)   -- 能用 (a)、(a,b)、(a,b,c)，单独查 b 用不上
   ```
4. **索引失效的 8 种写法**（逐条给 EXPLAIN 证据）：
   - 在索引列上做函数运算
   - 隐式类型转换（`user_id` 是 int，`user_id = '42'`）
   - 前导模糊 `LIKE '%xx'`
   - `OR` 连接非索引列
   - `!=` / `NOT IN`
   - 优化器认为全表扫描更快
